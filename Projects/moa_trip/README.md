# 🧳 모아트립 (moa_trip)

공공데이터(한국관광공사·기상청) 기반 **여행 일정 및 관광 정보 공유 플랫폼** — Django 팀 프로젝트

- **기간** : `2026.09.14` ~ `2026.09.22`
- **인원** : 4명 (팀 SOO-Team2)
- **팀 저장소** : [SOO-Team2/moa_trip](https://github.com/SOO-Team2/moa_trip)

---

## 🛠 기술 스택

| 구분 | 사용 기술 |
|---|---|
| Backend | Python, Django 4.2 |
| Database | MariaDB (mysqlclient) |
| Frontend | HTML, CSS, JavaScript (Django Template) |
| 외부 API | 한국관광공사 TourAPI (국문 관광정보 / 반려동물 동반여행), 기상청 단기·중기예보, 네이버 지도 API |
| 협업 | Git / GitHub (feature 브랜치 → PR → master) |

---

## ✨ 주요 기능

- **메인** : 추천 관광지(랜덤 정렬), 반려동물 동반 관광지
- **관광지 탐색** : 지역·반려동물·평점 필터, 후기순 등 정렬
- **관광지 상세** : 관광지 정보·이미지 갤러리, 날씨 예보, 후기 작성/삭제, 즐겨찾기
- **여행 일정 플래너** : 일정 생성, 장소 추가/삭제, 방문 시간 지정, 즐겨찾기에서 바로 추가
- **마이페이지** : 대시보드, 즐겨찾기·후기 목록 (최신순)
- **회원** : 회원가입(비밀번호 해싱), 로그인/로그아웃
- **관리자 페이지**

---

## 🗄 DB 구조

```
USERS ─┬─< FAVORITE >─┐
       ├─< REVIEW   >─┼── TOURISTSPOT >── REGION
       └─< ITINERARY ─< ITINERARY_TIME >─┘
```

| 테이블 | 설명 |
|---|---|
| USERS | 회원 |
| REGION | 지역 코드 |
| TOURISTSPOT | 관광지 (TourAPI 데이터) |
| FAVORITE | 회원 ↔ 관광지 즐겨찾기 |
| REVIEW | 관광지 후기 (별점, 사진) |
| ITINERARY | 여행 일정 |
| ITINERARY_TIME | 일정별 방문 장소·시간 (1:N) |

---

## 🙋 내가 맡은 부분

**DB 모델링**
- ERD 설계 및 테이블 정의 (회원·지역·관광지·즐겨찾기·후기·일정)
- 설계한 MariaDB 테이블을 Django 모델로 작성 (`db_table`, `db_column` 매핑)
- `ITINERARY_TIME`을 1:1 → 1:N 구조로 변경 (하루 일정에 여러 장소·방문 시간 저장)
- 기능에 맞춰 스키마 보완 : 비밀번호 해싱 대비 `PW` 길이 확장, 최신순 정렬용 `CREATE_DATE` 추가

**화면 (Template / CSS)**
- 공통 레이아웃 : `base.html`, 헤더
- 메인, 로그인, 탐색, 마이페이지, 관리자 페이지 화면 구성
- 로그인 ↔ 회원가입 탭을 화면 전환 없이 전환

**기능 (View / Model)**
- 회원가입 : 비밀번호 해싱, 가입일자 저장
- 탐색 페이지 : 지역·반려동물·평점 필터, 후기순 정렬
- 즐겨찾기 : 탐색 페이지에서 추가, 플래너와 연동
- 여행 일정 플래너 : 장소 추가/삭제, 방문 시간 추가 (`ITINERARY_TIME` 1:N 구조 반영)
- 후기 : 별점 UI와 DB 저장 로직 통합, 메인/탐색 페이지 평점·후기 수를 실제 데이터로 표시
- 상세 페이지 : 이미지 확대 팝업 + 화살표로 넘기기
- 마이페이지 : 대시보드, 즐겨찾기/후기 최신순 정렬

## 🔧 트러블슈팅

### 1. 일정 1건에 장소를 하나밖에 저장할 수 없는 스키마 문제

- **문제** : 하루 일정에 여러 관광지와 방문 시간을 넣어야 하는데, 두 번째 장소부터 저장되지 않음
- **원인** : `ITINERARY_TIME`이 `ITINERARY_CODE`를 **기본키이자 1:1 관계(`OneToOneField`)** 로 쓰고 있어서, 일정 하나당 행을 하나만 가질 수 있는 구조였음
- **해결** : 별도의 대리키 `ITINERARY_TIME_ID`(AutoField)를 기본키로 두고 `ITINERARY_CODE`는 일반 외래키(`ForeignKey`)로 바꿔 **1:N 관계로 재설계**
- **결과** : 일정 하나에 여러 장소·방문 시간 저장 가능, 플래너 화면도 여러 장소를 보여주도록 수정

### 2. 장소를 추가할 때마다 일정이 새로 생기는 중복 생성 문제

- **문제** : 같은 여행에 장소를 3곳 추가하면 일정이 3개로 쪼개져 저장됨
- **원인** : 장소 추가 요청마다 무조건 새 `ITINERARY_CODE`(UUID)를 발급해 `Itinerary`를 생성하고 있었음
- **해결**
  - 클라이언트가 현재 일정 코드를 함께 보내면 **기존 일정을 재사용**하고, 없을 때만 새로 생성하도록 분기
  - 일정 조회 시 `user_id` 조건을 함께 걸어 **다른 사람의 일정에는 장소를 추가할 수 없도록** 검증
  - 흩어져 있던 일정 삭제 URL/뷰를 하나의 API로 통합

### 3. 외부 API 데이터와 DB 후기 데이터가 연결되지 않던 문제

- **문제** : 메인·탐색 페이지 관광지 카드의 평점·후기 수가 하드코딩된 샘플 값이었고, "후기순" 정렬은 목록을 단순히 뒤집기만 했으며 평점 필터는 아예 적용되지 않음
- **원인** : 관광지 목록은 **TourAPI(외부 API)** 에서, 후기는 **우리 DB(`REVIEW`)** 에서 오는데 두 데이터를 합치는 로직이 없었음
- **해결**
  - 화면에 나올 관광지 ID를 모아 `Review.objects.filter(spot_id__in=...).values('spot_id').annotate(Avg, Count)`로 **한 번의 쿼리로 집계** (카드마다 쿼리를 보내는 N+1 문제 방지)
  - 집계 결과를 API 응답에 합친 뒤, 실제 `review_count` 기준 정렬과 최소 평점 필터 적용
- **결과** : 모든 카드에 실제 평점·후기 수가 표시되고 필터·정렬이 의도대로 동작
