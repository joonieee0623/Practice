# RAG & Function Calling 학습 노트

문서를 벡터로 저장하고, 검색해서, AI가 그 내용을 근거로 답하게 만드는 과정을 t11~t17에 걸쳐 단계별로 익혔다.
이 노트는 코드 설명보다 **배운 개념과 그 이유**를 정리한 것이다.

## 학습 흐름

| 단계 | 주제 | 핵심 개념 |
|---|---|---|
| t11 | 벡터 DB | 임베딩, 코사인 유사도, 메타데이터 필터 |
| t12 | RAG | 검색 결과를 프롬프트에 넣어 답변 생성 |
| t13 | PDF 입력 | 텍스트 추출, 청킹 |
| t14 | 이미지 PDF | OCR, Base64, Poppler, 재시도 |
| t15 | 구조 정리 | 테이블 존재 확인, `responses` API |
| t16 | RAG + 규칙 기반 분기 | 질문 번역, 키워드·점수로 외부 API 호출 결정 |
| t17 | RAG + Tools | AI가 도구를 직접 골라 호출하는 Function Calling |

```
[저장] 문서 → 조각내기(청킹) → 임베딩 → DB 저장
[질문] 질문 → 임베딩 → DB의 문서들과 유사도 비교 → 상위 k개 → 프롬프트에 삽입 → LLM 답변
```

---

## 1. 임베딩 (Embedding)
- 글을 숫자 목록(벡터)으로 바꾼 것이다. 이 프로젝트의 `text-embedding-3-small`은 글 하나를 약 1,536개 숫자로 바꾼다.
- 뜻이 비슷한 글은 숫자 목록도 비슷해진다. 단어가 달라도 의미가 가까우면 찾아낼 수 있는 이유이다.
- 키워드 검색은 글자가 같아야 찾지만, 임베딩 검색은 **의미**로 찾는다.

## 2. 코사인 유사도
- 두 벡터가 가리키는 방향이 얼마나 같은지 재는 값이다. 1에 가까울수록 비슷하다.
- 계산식은 `내적 ÷ (두 벡터 길이의 곱)`이다.
- 길이가 아니라 방향을 비교하므로, 글의 길이가 달라도 의미만 공정하게 비교할 수 있다.

## 3. 벡터 저장소
- 임베딩을 저장하고 비슷한 것을 찾아 주는 곳이다.
- 이 프로젝트는 전용 벡터 DB 없이 MariaDB 테이블에 임베딩을 JSON 문자열로 넣고, 파이썬이 모든 행을 읽어 유사도를 직접 계산한다.
- 원리를 눈으로 확인하기에 좋지만, 데이터가 많아지면 전체를 읽는 방식이라 느려진다. 실무에서는 벡터 인덱스나 전용 벡터 DB를 쓴다.
- 테이블 열: `text`(원문), `embedding`(숫자 목록), `metadata`(꼬리표).

## 4. 메타데이터와 필터
- 문서에 붙이는 꼬리표이다. 예: `{"author": "john", "type": "blog"}`, `{"source": "pdf"}`.
- 검색 때 조건을 걸어 특정 문서만 후보로 삼을 수 있다. 출처별, 작성자별 검색이 가능해진다.

## 5. RAG (검색 증강 생성)
- LLM은 내 문서를 모른다. 그래서 질문과 관련된 문서를 먼저 찾아 프롬프트에 붙여 주고 "이 문서를 근거로 답하라"고 시킨다.
- 얻는 효과: 최신·내부 정보를 반영할 수 있고, 지어낸 답(환각)이 줄어든다.
- 프롬프트의 기본 틀: `[문서 내용]` + `[질문]` + "문서를 근거로 답하세요".
- 검색 결과가 없을 때의 처리(안내 문구, 다른 수단)를 따로 정해 두어야 한다.

## 6. 청킹 (문서 쪼개기)
- 긴 문서를 검색하기 좋은 크기로 나누는 일이다. 너무 크면 핵심이 묻히고, 너무 작으면 문맥이 끊긴다.
- t13~t14는 줄바꿈 단위로 나눴다. 간단하지만 한 문장이 두 줄에 걸치면 끊기는 한계가 있다.
- 실무에서는 글자 수 기준에 일부 겹침(overlap)을 두고 나눈다.

## 7. PDF 처리: 텍스트형과 이미지형
- 텍스트형 PDF: `pypdf`로 글자를 바로 뽑는다.
- 이미지형(스캔본) PDF: 글자가 아니라 사진이라 `pypdf`로는 빈 결과가 나온다. OCR이 필요하다.

## 8. OCR 파이프라인 (t14)
1. PDF를 페이지별 이미지로 변환한다. (`pdf2image` + Poppler)
2. 이미지를 Base64 문자열로 바꾼다. 이진 데이터를 글자로 표현해 API 요청에 실을 수 있게 하는 방식이다.
3. `gpt-4o`에 이미지와 "텍스트만 추출해 줘"를 보낸다. 별도 OCR 프로그램 없이 모델의 이미지 인식 기능을 쓴다.
4. 결과를 줄 단위로 나눠 저장한다.

- **Poppler**: PDF를 다루는 외부 프로그램이다. `pdf2image`는 Poppler를 호출하는 껍데기일 뿐이라 따로 설치해야 하고, 경로를 PATH나 `poppler_path`로 알려 줘야 한다.
- **재시도(RateLimit)**: API 호출이 몰리면 속도 제한 오류가 난다. 대기 시간을 점점 늘려(1초 → 2.5초 → 4초...) 다시 시도하는 방식이 기본 대처법이다.

## 9. Function Calling / Tools
- LLM은 실시간 날씨나 계산 같은 일을 직접 못 한다. 그런 일을 우리 코드의 함수에 맡기는 방법이다.
- 중요한 점: **LLM이 함수를 실행하는 것이 아니다.** LLM은 "이 함수를 이 인자로 불러 달라"고 요청만 하고, 실제 실행은 우리 코드가 한다.
- 흐름: 함수 설명서(스키마)를 AI에게 전달 → AI가 호출 요청 → 코드가 함수 실행 → 결과를 AI(또는 코드)가 자연어로 정리.
- **함수 설명서(JSON 스키마)**: 이름, 설명, 매개변수를 적은 것이다. AI는 이 설명을 읽고 도구를 쓸지, 어떤 인자를 넣을지 판단한다. 설명이 정확할수록 호출이 정확해진다.

### t16과 t17의 차이
| | t16 | t17 |
|---|---|---|
| 호출 판단 | 코드가 규칙으로 결정 (날씨 키워드, 유사도 점수 0.3 미만) | AI가 질문을 보고 결정 |
| 장점 | 단순하고 예측 가능 | 질문 표현이 달라도 유연하게 대응 |
| 단점 | 규칙에 없는 표현을 놓침 | 호출 형식을 정확히 맞춰야 함 |

- t16은 엄밀히는 Function Calling이 아니라 규칙 기반 분기이다. t17부터가 진짜 Tools 방식이다.

## 10. 질문 번역과 도시명 추출
- 질문을 영어로 번역한 뒤 검색하고, 영어 문장에서 도시명을 뽑는다.
- 이유: 날씨 API는 영문 도시명을 요구한다.
- 추출한 결과는 영문자만 남기고(`re.sub`), 비어 있으면 기본값 `Seoul`을 쓰면 오류를 줄일 수 있다.

## 11. OpenAI API 호출 방식의 변화
- 예전: `client.chat.completions.create(messages=[...])` → 답은 `choices[0].message.content`
- 최신: `client.responses.create(model=..., input=...)` → 답은 `output_text`
- Tools 형식도 두 방식이 다르다. `responses` API에서는 도구 정의와 호출 결과의 항목 이름이 `chat.completions`와 다를 수 있으므로, 오류가 나면 공식 문서의 형식을 먼저 확인한다.

## 12. 환경변수와 보안
- API 키, DB 비밀번호는 코드에 쓰지 않고 `.env`에 둔 뒤 `os.getenv`로 읽는다.
- `.env`는 `.gitignore`에 넣어 GitHub에 올라가지 않게 한다.
- 용량이 큰 외부 프로그램(Poppler)과 실행 중 생기는 임시 파일(`uploaded.pdf`)도 `.gitignore`로 제외한다.

## 13. 한계와 개선 방향
- 검색 시 테이블 전체를 읽는다. → 벡터 인덱스, 전용 벡터 DB
- 문서마다 임베딩 API를 호출한다. → 배치 호출로 시간·비용 절감
- 줄바꿈 청킹은 문맥이 끊긴다. → 글자 수 + 겹침 기반 분할
